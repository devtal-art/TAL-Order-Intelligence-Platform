# Order Intelligence Platform — REST API Contract (Version 1)

**Status:** Draft for sign-off · **Audience:** Frontend + Backend · **Scope:** Contract only — no implementation.

This document is the single source of truth for the v1 HTTP API. Once agreed, both
`client/` and `server/` build against it. Changing a shape here is a contract change
and must be versioned (see [Versioning](#versioning)).

> **Not implemented.** No controllers, services, models, or business logic exist yet.
> This is the specification only.

---

## 1. Conventions

### Base URL & versioning
- All v1 endpoints are namespaced under **`/api/v1`**.
  Example: `POST /api/v1/resolve`.
- The existing infrastructure health route (`GET /api/health`) is retained as an
  unversioned liveness probe; the versioned `GET /api/v1/health` below is the
  documented app health endpoint.
- Breaking changes ship under `/api/v2`. v1 stays stable and additive-only.

### Content types
- Requests/responses are **`application/json; charset=utf-8`**, except the catalog
  upload, which is **`multipart/form-data`**.
- All timestamps are **ISO 8601 UTC** strings (e.g. `2026-07-03T05:16:10.177Z`).
- IDs are opaque strings with a type prefix (`cat_…`, `map_…`, `exp_…`). Clients
  must treat them as opaque.

### Authentication & authorization (contract placeholder)
Auth is **not implemented in v1** but the contract reserves its shape so it can be
added without breaking clients:
- Future scheme: `Authorization: Bearer <token>`.
- Each endpoint below declares a **Required role** (`public`, `agent`, `admin`).
  Until auth lands, all roles resolve to an anonymous system user; `approvedBy` and
  `uploadedBy` are recorded as `"system"`.
- **Attribution is never taken from the request body.** `approvedBy` / `uploadedBy`
  derive from the authenticated principal only.

### Standard success envelope
Successful responses return the resource directly (no wrapper), with the documented
HTTP status. Collections use:
```json
{ "data": [ ... ], "meta": { "total": 0, "page": 1, "pageSize": 50 } }
```

### Standard error envelope
Every non-2xx response uses this shape:
```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Human-readable summary of what went wrong.",
    "details": [
      { "field": "itemNo", "issue": "not found in the active catalog" }
    ],
    "requestId": "req_9f2c1a"
  }
}
```
- `code` — stable machine-readable enum (see [Error codes](#error-codes)).
- `details` — optional, field-level; present for validation errors.
- `requestId` — correlation id, also returned as the `X-Request-Id` response header.

### Error codes
| `code` | HTTP | Meaning |
|---|---|---|
| `VALIDATION_ERROR` | 400 | Malformed/invalid request body or params. |
| `UNSUPPORTED_MEDIA_TYPE` | 415 | Wrong `Content-Type` (e.g. not multipart for upload). |
| `PAYLOAD_TOO_LARGE` | 413 | Upload/body exceeds size limit. |
| `UNAUTHORIZED` | 401 | Missing/invalid credentials (future). |
| `FORBIDDEN` | 403 | Authenticated but wrong role (future). |
| `NOT_FOUND` | 404 | Resource/route does not exist. |
| `CONFLICT` | 409 | State conflict (e.g. duplicate mapping). |
| `UNPROCESSABLE` | 422 | Well-formed but semantically invalid (e.g. item not in catalog). |
| `NO_ACTIVE_CATALOG` | 409 | An operation needs a catalog but none is active. |
| `RATE_LIMITED` | 429 | Too many requests (future). |
| `INTERNAL_ERROR` | 500 | Unexpected server error. |
| `SERVICE_UNAVAILABLE` | 503 | Dependency (DB) down. |

### Normalization note
The server owns a single canonical **name-normalization** function used at CSV
ingest, at resolution lookup, and at mapping creation. Clients always send **raw**
names; the server normalizes internally. Clients never compute normalization or
match scores.

### Idempotency & concurrency
- `POST /catalog` is **not** idempotent — each call replaces the catalog and creates
  a new version.
- `POST /mappings` is guarded by a uniqueness constraint on the normalized email
  product name; concurrent duplicates resolve to a single winner (`409` for losers).
- Reads (`GET`) are always safe and cacheable via `ETag` where noted.

## 3. Shared Object Schemas

Referenced by multiple endpoints.

**`ProductCandidate`**
```json
{ "websiteProductName": "Widget, Blue, 0.5L", "itemNo": "WB-500", "matchPercent": 88 }
```
`matchPercent` is an integer 0–100, a **ranking aid only** — never a recommendation.

**`ResolvedMatch`** (an approved/selected result)
```json
{ "websiteProductName": "Widget, Blue, 0.5L", "itemNo": "WB-500", "mappingId": "map_abc" }
```

**`Mapping`**
```json
{
  "id": "map_abc",
  "emailProductName": "Blue Widget 500ml",
  "websiteProductName": "Widget, Blue, 0.5L",
  "itemNo": "WB-500",
  "approvedBy": "system",
  "approvedDate": "2026-07-03T05:16:10.177Z",
  "timesUsed": 0,
  "status": "active"
}
```

**`CatalogStatus`**
```json
{
  "version": "cat_2026_07_03_a",
  "filename": "products_2026_07_03.csv",
  "productCount": 4812,
  "uploadedBy": "system",
  "uploadedAt": "2026-07-03T09:14:00.000Z",
  "status": "active"
}
```

## 4. Endpoint Specifications

Each endpoint documents: **Method · URL · Purpose · Required role · Request · Response ·
Validation · Errors · Success · Future notes.**

---

### 4.1 Health Check
- **Endpoint:** Health Check
- **Method:** `GET`
- **URL:** `/api/v1/health`
- **Purpose:** Liveness/readiness signal for monitoring and the client boot check.
- **Required role:** public
- **Request Body:** _none_
- **Success Response — `200 OK`:**
```json
{ "status": "ok", "service": "order-intelligence-server", "version": "v1", "timestamp": "2026-07-03T05:16:10.177Z" }
```
- **Validation Rules:** none.
- **Possible Errors:** `503 SERVICE_UNAVAILABLE` (a declared dependency is down; body
  may include `{ "status": "degraded", "dependencies": { "db": "down" } }`).
- **Future Expansion:** add per-dependency readiness (DB, storage), build SHA, and a
  separate `/health/ready` vs `/health/live` split for orchestration.

---

### 4.2 Upload Product Catalog
- **Endpoint:** Upload Catalog
- **Method:** `POST`
- **URL:** `/api/v1/catalog`
- **Purpose:** Replace the entire active product catalog with the uploaded CSV. Creates
  a new catalog version and atomically activates it; the previous version is retired.
- **Required role:** admin
- **Request Body:** `multipart/form-data`
  - `file` — the CSV (required). Must contain at least the columns `item_no` and `name`.
  - Optional form fields: `filenameOverride` (string).
- **CSV expectations:** header row required; `item_no` and `name` columns present
  (case-insensitive, order-independent); extra columns ignored in v1.
- **Success Response — `201 Created`:**
```json
{
  "version": "cat_2026_07_03_a",
  "filename": "products_2026_07_03.csv",
  "productCount": 4812,
  "rejectedRows": 3,
  "uploadedBy": "system",
  "uploadedAt": "2026-07-03T09:14:00.000Z",
  "status": "active"
}
```
- **Validation Rules:**
  - `Content-Type` must be `multipart/form-data` → else `415`.
  - `file` present and non-empty → else `400`.
  - Extension `.csv` and parseable as CSV → else `422`.
  - Required headers present → else `422` with `details` naming the missing column(s).
  - At least **1** valid data row → else `422 VALIDATION_ERROR` ("empty catalog rejected").
  - Size ≤ configured limit (e.g. 20 MB) → else `413`.
  - Malformed rows are **reported** in `rejectedRows`, not silently dropped; a fully
    invalid file is rejected without replacing the live catalog.
- **Possible Errors:** `400`, `413`, `415`, `422`, `403` (non-admin), `500`.
- **Atomicity guarantee (contract):** if the request fails at any stage, the previously
  active catalog remains active and unchanged.
- **Future Expansion:** dry-run/preview mode (`?validateOnly=true`), per-client catalogs,
  async ingestion with a job id for very large files, retaining N prior versions,
  `GET /catalog/versions` history, delta diff vs previous version.

---

### 4.3 Catalog Status *(supporting)*
- **Endpoint:** Catalog Status
- **Method:** `GET`
- **URL:** `/api/v1/catalog/status`
- **Purpose:** Return metadata about the currently active catalog so agents can see
  freshness ("today 09:14 · 4,812 products") before processing an order.
- **Required role:** agent
- **Request Body:** _none_
- **Success Response — `200 OK`:** a `CatalogStatus` object, **or** when none exists:
```json
{ "status": "none", "version": null, "productCount": 0, "uploadedAt": null }
```
- **Validation Rules:** none.
- **Possible Errors:** `500`, `503`.
- **Future Expansion:** `ETag`/`Last-Modified` for cheap polling; include the
  normalization ruleset version so clients can display "catalog + rules" freshness.

---

### 4.4 Search Catalog *(supporting)*
- **Endpoint:** Search Catalog
- **Method:** `GET`
- **URL:** `/api/v1/catalog/products?query=<string>&limit=<n>`
- **Purpose:** Free-text search across the active catalog, powering the agent's
  **manual search** escape hatch when the resolver's Top-5 is wrong.
- **Required role:** agent
- **Request Body:** _none_ (query params).
- **Query params:** `query` (required, min length 1), `limit` (optional, default 10,
  max 50).
- **Success Response — `200 OK`:**
```json
{ "data": [ { "websiteProductName": "Widget, Blue, 0.5L", "itemNo": "WB-500", "matchPercent": 91 } ],
  "meta": { "total": 12, "returned": 10 } }
```
- **Validation Rules:** `query` non-empty → else `400`; `limit` within range → else `400`.
- **Possible Errors:** `400`, `409 NO_ACTIVE_CATALOG`, `500`.
- **Future Expansion:** pagination cursor, filters (category/brand), fuzzy vs exact toggle.

---

### 4.5 Resolve Products
- **Endpoint:** Resolve Products
- **Method:** `POST`
- **URL:** `/api/v1/resolve`
- **Purpose:** The core workhorse. For each extracted email product name, return either
  a previously **approved** mapping (100%) or the **Top-5** closest catalog candidates.
  One order = one call. **Never auto-selects, never auto-approves.**
- **Required role:** agent
- **Request Body:**
```json
{
  "products": [
    { "lineId": "1", "name": "Blue Widget 500ml", "package": "Case of 12", "qty": 3 },
    { "lineId": "2", "name": "Green Gadget" }
  ]
}
```
  - `products` — array, 1..N (max e.g. 200).
  - `lineId` — client-supplied echo key (required, unique within request).
  - `name` — raw email product name (required, non-empty).
  - `package`, `qty` — optional disambiguation context; not required.
  - **Only product names/context are sent** — no customer, address, or financial data
    crosses the trust boundary.
- **Success Response — `200 OK`:**
```json
{
  "catalogVersion": "cat_2026_07_03_a",
  "results": [
    {
      "lineId": "1",
      "emailProductName": "Blue Widget 500ml",
      "status": "approved",
      "confidence": 100,
      "reason": "Previously approved manually.",
      "match": { "websiteProductName": "Widget, Blue, 0.5L", "itemNo": "WB-500", "mappingId": "map_abc" },
      "candidates": []
    },
    {
      "lineId": "2",
      "emailProductName": "Green Gadget",
      "status": "needs_review",
      "confidence": null,
      "reason": "No approved mapping; showing closest catalog matches.",
      "match": null,
      "candidates": [
        { "websiteProductName": "Gadget Green", "itemNo": "GG-1", "matchPercent": 88 }
      ]
    },
    {
      "lineId": "3",
      "emailProductName": "Zzz Unknown",
      "status": "no_match",
      "confidence": null,
      "reason": "No candidate cleared the minimum match threshold.",
      "match": null,
      "candidates": []
    }
  ]
}
```
  - `status` enum: `approved` | `needs_review` | `no_match`.
  - `candidates` is ordered best-first, length 0–5.
- **Validation Rules:**
  - `products` present, non-empty, within max size → else `400` / `413`.
  - Each item has non-empty `name` and unique `lineId` → else `400` with `details`.
  - An **active catalog must exist** → else `409 NO_ACTIVE_CATALOG`.
- **Possible Errors:** `400`, `409 NO_ACTIVE_CATALOG`, `413`, `422`, `500`.
- **Future Expansion:** configurable `topN`, per-client mapping scope, return the match
  algorithm/version used, partial streaming for very large orders, caching by
  `(normalizedName, catalogVersion)`.

### 4.6 Match Single *(supporting)*
- **Endpoint:** Match Single
- **Method:** `POST`
- **URL:** `/api/v1/match`
- **Purpose:** Re-run matching for one product name against the active catalog (used
  when an agent tweaks a name or re-searches a single stubborn item). Same scoring as
  `/resolve` but for one input and **without** the approved-mapping short-circuit.
- **Required role:** agent
- **Request Body:** `{ "name": "Grn Gadget", "topN": 5 }`
- **Success Response — `200 OK`:** `{ "candidates": [ ProductCandidate, ... ] }`
- **Validation Rules:** `name` non-empty → else `400`; `topN` 1–20 → else `400`;
  active catalog required → else `409`.
- **Possible Errors:** `400`, `409 NO_ACTIVE_CATALOG`, `500`.
- **Future Expansion:** merge into `/resolve` via a `mode` flag if the two converge.

---

### 4.7 Create Approval (Mapping)
- **Endpoint:** Create Approval
- **Method:** `POST`
- **URL:** `/api/v1/mappings`
- **Purpose:** Persist a human-confirmed mapping so the same email product resolves
  instantly at 100% next time. Written **only** after a manual selection.
- **Required role:** agent
- **Request Body:**
```json
{
  "emailProductName": "Green Gadget",
  "websiteProductName": "Gadget Green",
  "itemNo": "GG-1"
}
```
  - `approvedBy` is **not** accepted in the body — it is taken from the authenticated
    principal (currently `"system"`).
- **Success Response — `201 Created`:** a full `Mapping` object with `timesUsed: 0`,
  server-set `approvedDate`, and `status: "active"`.
- **Validation Rules:**
  - `emailProductName` non-empty → else `400`.
  - `itemNo` non-empty **and present in the active catalog** → else `422`.
  - `websiteProductName` non-empty → else `400`.
  - No active mapping may already exist for the normalized `emailProductName`
    → else `409 CONFLICT` (response includes the existing mapping). Use `PATCH` to change.
- **Possible Errors:** `400`, `409 CONFLICT`, `409 NO_ACTIVE_CATALOG`, `422`, `403`, `500`.
- **Future Expansion:** per-client scope (`clientId`), package/variant in the key,
  bulk seed endpoint (`POST /mappings/bulk`), optional `overwrite: true` to upsert.

---

### 4.8 List / Search Mappings *(supporting)*
- **Endpoint:** List Mappings
- **Method:** `GET`
- **URL:** `/api/v1/mappings?query=<string>&page=<n>&pageSize=<n>&status=active`
- **Purpose:** Browse/search the approved-mapping database for audit and management.
- **Required role:** agent (read); management edits are admin-only (4.9/4.10).
- **Request Body:** _none_ (query params).
- **Success Response — `200 OK`:** `{ "data": [ Mapping, ... ], "meta": { "total", "page", "pageSize" } }`
- **Validation Rules:** pagination params within bounds → else `400`.
- **Possible Errors:** `400`, `500`.
- **Future Expansion:** sort by `timesUsed`, filter by `approvedBy`/date range, export CSV.

---

### 4.9 Update Mapping *(supporting)*
- **Endpoint:** Update Mapping
- **Method:** `PATCH`
- **URL:** `/api/v1/mappings/:id`
- **Purpose:** Correct a wrong mapping (e.g. new item number) with an audit trail.
- **Required role:** admin
- **Request Body:** any of `{ "websiteProductName", "itemNo", "status" }`.
- **Success Response — `200 OK`:** the updated `Mapping`.
- **Validation Rules:** `:id` exists → else `404`; new `itemNo` (if given) exists in the
  active catalog → else `422`; `status` in enum `active|retired` → else `400`.
- **Possible Errors:** `400`, `404`, `422`, `403`, `500`.
- **Future Expansion:** store revision history; reason/comment field for the change.

---

### 4.10 Retire Mapping *(supporting)*
- **Endpoint:** Retire Mapping
- **Method:** `DELETE`
- **URL:** `/api/v1/mappings/:id`
- **Purpose:** Retire a bad mapping. **Soft-delete** (sets `status: "retired"`) to
  preserve history and `timesUsed` analytics.
- **Required role:** admin
- **Request Body:** _none_
- **Success Response — `200 OK`** `{ "id": "map_abc", "status": "retired" }` (or `204 No Content`).
- **Validation Rules:** `:id` exists → else `404`.
- **Possible Errors:** `404`, `403`, `500`.
- **Future Expansion:** hard-delete for admins with a separate `?purge=true`; restore endpoint.

### 4.11 Prepare Export
- **Endpoint:** Prepare Export
- **Method:** `POST`
- **URL:** `/api/v1/export/prepare`
- **Purpose:** Finalize a fully-resolved order **before** the client builds the Excel.
  Validates that every line has an item number, increments `timesUsed` for the mappings
  actually used, and returns the enriched line data (item numbers + website names) the
  client embeds into the workbook. Optionally records an export/audit entry.
- **Required role:** agent
- **Request Body:**
```json
{
  "orderRef": "PO-10432",
  "items": [
    { "lineId": "1", "emailProductName": "Blue Widget 500ml", "itemNo": "WB-500", "mappingId": "map_abc", "source": "approved" },
    { "lineId": "2", "emailProductName": "Green Gadget", "itemNo": "GG-1", "mappingId": "map_def", "source": "manual" }
  ]
}
```
  - `source` enum: `approved` | `manual` | `skipped`.
  - `itemNo` required unless `source: "skipped"` (see Open Decision OD-2).
- **Success Response — `200 OK`:**
```json
{
  "exportId": "exp_77c1",
  "preparedAt": "2026-07-03T05:20:00.000Z",
  "orderRef": "PO-10432",
  "items": [
    { "lineId": "1", "itemNo": "WB-500", "websiteProductName": "Widget, Blue, 0.5L" },
    { "lineId": "2", "itemNo": "GG-1", "websiteProductName": "Gadget Green" }
  ],
  "timesUsedUpdated": 2,
  "warnings": []
}
```
- **Validation Rules:**
  - `items` non-empty → else `400`.
  - Every non-skipped item has an `itemNo` → else `422` (this enforces the "export gate").
  - Referenced `itemNo`s should exist in the active catalog; stale ones are returned in
    `warnings` (not a hard failure) so the client can flag them — see OD-3.
- **Possible Errors:** `400`, `422`, `409 NO_ACTIVE_CATALOG`, `500`.
- **Note on responsibility:** the Excel file itself is still generated **client-side**
  (unchanged `buildXLSX`). This endpoint prepares/validates data and updates counters;
  it does not return a file in v1.
- **Future Expansion:** server-side workbook/CSV generation returning a file or signed
  URL; persist full export history for metrics ("time saved"); idempotency key to avoid
  double-increment on retry.

## 5. Missing Endpoints Identified

The five headline features cannot function end-to-end with only five endpoints. These
gaps are **included in the v1 contract above** and called out here explicitly:

1. **`GET /api/v1/catalog/status`** (4.3) — the Catalog Upload feature is write-only
   without it; agents need to see freshness, and the homepage Step 1 card is a placeholder
   waiting for exactly this data.
2. **`GET /api/v1/catalog/products`** (4.4) — Resolution's "manual search" escape hatch
   is impossible without a catalog search endpoint.
3. **`POST /api/v1/match`** (4.6) — re-searching a single product after an agent edits
   the name; otherwise they must re-resolve the whole order.
4. **`GET /api/v1/mappings`** (4.8) — the Approval feature is write-only without a way to
   view/audit what has been approved.
5. **`PATCH` / `DELETE /api/v1/mappings/:id`** (4.9/4.10) — approvals are human decisions
   and *will* be wrong sometimes; there must be a correction/retirement path.

Deferred beyond v1 (flagged now so the contract can grow additively):
- **Auth**: `POST /api/v1/auth/login`, `GET /api/v1/auth/me`, plus role management.
- **Catalog history**: `GET /api/v1/catalog/versions`, `GET /api/v1/catalog/versions/:id`.
- **Bulk mapping seed**: `POST /api/v1/mappings/bulk` (day-one cold-start problem).
- **Export history/metrics**: `GET /api/v1/exports`, `GET /api/v1/metrics` (time-saved).

## 6. Open Decisions Affecting This Contract

These must be answered before implementation; each changes a shape above.

- **OD-1 — Mapping scope:** global (current contract) vs per-client. Per-client adds a
  required `clientId` to `/resolve`, `/mappings`, and the uniqueness key.
- **OD-2 — Skip semantics:** may `/export/prepare` accept `source: "skipped"` items with
  no `itemNo` (export proceeds with a blank), or is a resolved item required for every
  line (export blocked)? Current contract allows skip.
- **OD-3 — Stale item handling:** when a mapping's `itemNo` no longer exists in the active
  catalog, do we `warn` (current contract) or hard-`422`? Recommendation: warn, never
  silently ship a dead number.
- **OD-4 — `timesUsed` increment point:** on `/export/prepare` (current contract) vs on
  `/resolve` serve. Recommendation: on export = "actually used."
- **OD-5 — Match threshold:** the minimum `matchPercent` below which `/resolve` returns
  `no_match` instead of weak candidates. Server-owned config; expose in response meta?

## 7. Change Control

- v1 is **additive-only**: new optional fields and new endpoints are allowed; removing or
  renaming fields, or changing types/enums, requires **v2**.
- Every response carries `X-Request-Id`; every error carries a stable `code`. Clients must
  branch on `code`, never on `message` text.
